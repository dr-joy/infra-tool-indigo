### 1.1. Provider — một `AutomationResultsStore` duy nhất ở App root

```tsx
// src/automation-results-context.tsx (mới)
import { createContext, useContext, useState, useEffect, useSyncExternalStore, type ReactNode } from 'react';
import { AutomationResultsStore } from './lib/automation-results-store';
import type { CoordinatorState } from './lib/automation-results-reducer';

const Ctx = createContext<AutomationResultsStore | null>(null);

export function AutomationResultsProvider({ children }: { children: ReactNode }) {
  const [store] = useState(() => new AutomationResultsStore()); // tạo ĐÚNG 1 LẦN, không side effect trong constructor
  useEffect(() => { store.start(); return () => store.stop(); }, [store]); // side effect ở ĐÚNG chỗ React cho phép
  return <Ctx.Provider value={store}>{children}</Ctx.Provider>;
}

export function useAutomationResultsStore(): AutomationResultsStore {
  const store = useContext(Ctx);
  if (!store) throw new Error('useAutomationResultsStore phải nằm trong AutomationResultsProvider');
  return store;
}

export function useAutomationResultsState(): CoordinatorState {
  const store = useAutomationResultsStore();
  return useSyncExternalStore(store.subscribe, store.getSnapshot); // đã kiểm tương thích ở lát 3
}
```

Bọc ở `src/main.tsx` — component App gốc bọc `<AutomationResultsProvider>` MỘT LẦN quanh toàn cây; cả
`main.tsx` (đọc `visibleQueue`/`isSyncing`/`errorsByKey` để vẽ hàng đợi/banner) lẫn `useAutomation()` (gọi
lệnh cho phiên tương tác) đều lấy CÙNG instance qua Context — không có "mỗi hook một store" như blocker đã
sửa từ vòng thiết kế trước.

StrictMode: `useState(() => new Store())` tạo store không side effect; `store.start()/stop()` đã kiểm
idempotent ở lát 3 (test "gọi 2 lần vẫn idempotent", "pre-start + stop() vẫn drain đúng") — mount→unmount→mount
của StrictMode dev an toàn, không cần code thêm gì ở tầng Provider.

### 2.1. Blocker — lát 4 phải chuyển owner thật, không được để hai orchestration cùng hoạt động

### 2.2. Blocker — bảng `/execute`/recovery chưa đủ để implement mà không đoán

Code hiện tại không chỉ có đường “`/execute` trả occurrenceKey rồi attach”. `executeAutomation()` còn xử lý
response terminal thiếu key, status lạ, lỗi HTTP/mất response và reload dashboard; `phanChieuTuServer()` còn phân
biệt terminal/non-terminal, đồng thời cố ý **không tự tính occurrence key** khi server không còn giữ key
(`useAutomation.ts:249–349`). Brief mới phải có decision table tối thiểu cho các ca sau:

1. `/execute` trả terminal hợp lệ + `occurrenceKey` hợp lệ → direct one-shot `ganVaoPhien` và UI tạm thời trong
   lúc chờ lookup;
2. terminal hợp lệ nhưng thiếu key → không attach key đoán; đóng/bàn giao cho background feed với thông báo;
3. HTTP/network error sau khi server có thể đã claim → reload dashboard; nếu còn non-terminal + key server thì
   `choTerminalTrongPhien`, nếu terminal/không còn key thì bàn giao feed;
4. dashboard có non-terminal + key nhưng `automationUpdatedAt` thiếu/sai → không attach, đóng/bàn giao session,
   toast “cần kiểm tra thủ công”, queue không bị chặn;
5. status lạ hoặc reload thất bại/không tìm thấy task → fail-safe bàn giao feed, tuyệt đối không dựng `failed`
   có nút retry execute.

Deadline cũng phải có owner code cụ thể. Thiết kế đã chốt công thức
`automationUpdatedAt + 10 phút + 2×30s + 30s`, nhưng code hiện tại để `RUNNING_LEASE_MINUTES` ở
`server/lib/automation-helpers.ts`, `TICK_INTERVAL_MS` ở `server/lib/automation-scheduler.ts`, còn
`POLL_INTERVAL_MS` là hằng private trong driver. Brief phải chỉ rõ helper/hằng dùng chung nào sẽ được tạo/export
(thiết kế trước đã đề xuất chuyển lease constant sang `server/types.ts`, nơi FE đã có pattern import), tránh FE
import module runtime server hoặc chép ba magic number. Đây là thay đổi tích hợp đã nằm trong thiết kế, không phải
DESIGN REOPEN; nếu buộc sửa public contract driver thì dừng theo §1.5.

### 2.3. Blocker — `isSyncing()` không tương đương `dangLamMoiKetQua`

`isSyncing(state)` hiện trả `state.fetch.current !== null` (`automation-results-reducer.ts:518`), tức là true cho
cả poll nền định kỳ. `dangLamMoiKetQua` cũ chỉ chặn UI trong foreground refresh sau reconcile. Thay thẳng nó vào
`dangCoModalKhac` như §1.2 sẽ làm một poll nền chậm (timeout tới 20 giây) ẩn/chặn popup kết quả dù queue đang có
item ready. Đây là đổi hành vi, không phải refactor tương đương.

Brief phải chọn và test một policy tường minh: background poll không được coi là “modal khác”; chỉ trạng thái
foreground/reconcile có nguy cơ snapshot cũ mới được chặn, hoặc dựa hoàn toàn vào selector visibility/CAS nếu
coordinator đã biểu diễn đủ. Thêm test deferred fetch: queue có item B ready, background poll đang bay/chậm thì B
vẫn hiển thị và thao tác được.

### 2.5. Mapping UI và test còn mơ hồ

§1.3 nói “bấm 1 dòng digest → `ganVaoPhien`”, trong khi UI hiện tại mỗi dòng chỉ có **Mở task** và **Đã xem**

`xacNhanDaXem`; không được biến thao tác mở task thành direct attach. Nếu muốn thêm thao tác xem chi tiết mới thì đó

### 4.1. Blocker — `choTerminalTrongPhien()` không phải Promise “chờ terminal”

§3.1 nói thay effect recovery cũ bằng “chờ Promise của `choTerminalTrongPhien`”; §3.2 nhánh 3 lại diễn giải
`true` là đã có snapshot terminal, `false` là hết hạn/bị detach. Contract thật không như vậy:

- `choTerminalTrongPhien()` chỉ đăng ký waiter cho **foreground lookup hiện tại**
  (`automation-results-store.ts:212–217`);
- mọi waiter của job được resolve `true` ngay khi HTTP job thành công, kể cả response rỗng và entry vẫn
  `{phase:'awaiting'}` (`automation-results-reducer.ts:309–318, 357–359`);
- deadline được sweep ở các poll sau, không gắn waiter nào, nên Promise ban đầu đã resolve từ lâu; `false` chỉ nói
  job HTTP fail/abort/store stop, không phải `not_found`.

Theo flow v2, lookup recovery đầu tiên trả `[]` hợp lệ sẽ resolve `true`, rồi UI cố đọc terminal hoặc kết thúc chờ
quá sớm — đúng ca recovery phổ biến nhất.

Brief v3 phải giữ một effect/subscription state-driven theo đúng key session:

- gọi command một lần để attach; Promise chỉ dùng để biết attempt lookup đầu tiên có chạy xong ở tầng transport;
- `snapshotState.phase === 'awaiting'` → tiếp tục giữ session chờ, các poll sau tự targeted lookup;
- `ready` → render terminal từ `entry.snapshot`;
- `detachReason` `not_found/confirmed_absent` → close/toast đúng một lần rồi consume reason;
- `refresh.failed` trong khi vẫn awaiting không được giả thành deadline; coordinator còn quyền retry ở nhịp sau.

Thêm test bắt buộc: lookup đầu trả `[]` và Promise resolve `true` nhưng session vẫn chờ; poll sau trả result thì
session mới terminal. Một test khác advance qua deadline để chứng minh close đi từ `detachReason`, không đi từ giá
trị Promise.

### 4.2. Blocker — vẫn bỏ sót terminal response thiếu `occurrenceKey`

Vòng trước yêu cầu riêng ca `/execute` trả terminal hợp lệ nhưng thiếu key. §3.2 nhánh 1 vẫn gọi thẳng
`store.ganVaoPhien(r.occurrenceKey)` trong khi type thật là `occurrenceKey?: string`. Nhánh reload chỉ chạy cho
status lạ/lỗi HTTP, nên terminal-known + key `undefined` không rơi vào nhánh 2–5 nào.

Khóa nhánh này rõ trong decision table: chỉ direct-attach khi key là string hợp lệ; thiếu/rỗng → không tự tính key,
đóng/bàn giao background feed với toast. Thêm đúng một regression test cho response `{status:'done'}` không key,
assert không gọi `ganVaoPhien`, không lookup key `undefined`, không dùng `report` làm kết quả authoritative.

### 4.3. Blocker — lifecycle reconcile ở nested cancel và nhánh `handle:null` đang sai

§3.4 nói `onCancelTask` phải `handle.cancel()` ngay vì “huỷ hẳn task”. Code thật ở `main.tsx:627, 638–650` cho
thấy callback này **chỉ mở popup xác nhận**; user có thể bấm đóng xác nhận và quay lại `PopupSuaTask`. Nếu cancel
handle ngay lúc mở confirm, popup sửa vẫn sống nhưng đã mất active reconcile; sau đó lưu/`AiKetQua.onDaXuLy` không
còn refresh đúng occurrence.

Flow đúng phải là:

- mở popup xác nhận → giữ nguyên `{task, handle}`;
- user đóng popup xác nhận → vẫn giữ handle;
- API huỷ task thành công rồi mới consume `handle.cancel()` và đóng popup sửa;
- API huỷ lỗi → giữ handle để user còn thử lại/quay lại sửa.

Ngoài ra `batDauReconcile()` trả `null` khi mở **từ một result** không được vẫn mở popup với `handle:null`. Entry
sẽ không có owner refresh sau thay đổi, tái tạo stale-result bug mà refactor đang chữa. Task mở bình thường vốn có
`handle:null` là hợp lệ; task mở từ result mà claim thất bại phải hiện thông báo và **không mở popup**.

Với direct session, thứ tự cũng phải atomic theo capability: gọi `batDauReconcile(key)` trước; chỉ khi nhận được
handle mới `thaKhoiPhien(key)` và chuyển UI sang popup sửa. Nếu detach trước rồi claim trả `null`, v2 vừa làm mất
owner direct vừa mở editor không có reconcile. Siết test cho cả “đóng confirm” và “confirm API lỗi/thành công”,
cùng ca direct claim thất bại không detach session.

### 4.4. Blocker — `finish()` lỗi làm item biến mất nhưng brief xoá luôn đường retry

§3.4 hứa `finish() === false` hiện banner “chưa đồng bộ lại được, thử lại”. Nhưng §3.5 lại nói nút refresh không
còn ở lát 4 và không định nghĩa owner/callback cho banner. Trong reducer, khi lookup sau `finish()` lỗi thì entry có
`refresh.status='failed'`; `isVisible()` đòi `refresh.status==='idle'`, nên occurrence biến khỏi queue. Nếu không có
UI đọc `errorsByKey()` và gọi `store.thuLaiLamMoi(key)`, user vừa mất item vừa không có đường phục hồi.

Brief v3 phải khóa state UI giữ `{occurrenceKey, message}` sau khi editor đóng, render banner/nút retry theo từng
key từ `errorsByKey(state)`, và nút gọi `thuLaiLamMoi(key)`. Success thì banner tự dọn theo state authoritative;
failure tiếp tục giữ đúng key/message. Không được dùng một boolean/toast không có capability retry. Test A+B:
finish A lỗi → banner A + B vẫn thao tác được; retry A thành công → banner dọn, queue phản ánh snapshot mới; không
retry nhầm B.

### 4.5. Scope hằng số — hướng đúng nhưng phải gọi đúng là thay public surface driver

Chuyển lease/tick sang module shared thuần là hợp lý. Tuy nhiên `export POLL_INTERVAL_MS` là sửa public surface của

## 54. Leader ↔ Codex: định hướng lại BL-004 — form là luồng chính, AI hỏi trong app, CLI chỉ dự phòng

### Nói bằng lời thường

Nhu cầu thực tế của Leader chủ yếu là những automation đã biết trước người dùng cần cung cấp thông tin gì. App nên hiển thị form đơn giản, kết hợp câu trả lời với dữ liệu BE đã tính toán, rồi cho AI đề xuất việc cần làm. Chỉ một số ít trường hợp còn mơ hồ mới để AI hỏi thêm ngay trong app; cửa sổ Claude Code không nên là luồng chính. Phần khó như dùng cùng một người để viết tên, mention và gán ticket phải do BE quản lý bằng dữ liệu có cấu trúc, còn UI chỉ hiển thị form và bản xem trước dễ hiểu.

### 54.1. Tỷ lệ sử dụng và luồng đề xuất

- Khoảng **90%**: thiếu trường biết trước → dùng form theo loại automation.
- Khoảng **10%**: thông tin còn mơ hồ → AI trả `needs_input` và hỏi ngay trong app.
- Chỉ trường hợp hỏi đáp dài, cần điều tra mở hoặc thay đổi mục tiêu nhiều lần mới cân nhắc mở Claude Code/CLI tương tác.

Luồng mục tiêu:

```text
User chọn loại automation
→ app hiển thị form nền
→ BE lấy context hệ thống và kiểm tra dữ liệu còn thiếu
→ nếu cần, app hiển thị form bổ sung hoặc câu hỏi AI
→ user chọn “Lưu & kiểm tra lại ngay”
→ AI trả kế hoạch hành động có cấu trúc
→ app hiển thị preview dễ hiểu
→ user phê duyệt
→ BE/connector thực hiện
→ app hiển thị kết quả từng action
```

### 54.2. BE biết form nào bằng Automation Definition Registry

BE không tự đoán schema. Mỗi `automationType` có definition gồm:

- input schema;
- context builder;
- prompt/template;
- connector được phép;
- action được phép.

Task không cần user nhập có schema rỗng. Schema cần có version để task/occurrence cũ không bị thay nghĩa khi definition thay đổi.

### 54.3. Form gồm phần nền và phần phát sinh theo từng lần chạy

Form cố định không đủ vì cùng một loại automation, lần này có thể thiếu người cần xác nhận, lần khác lại thiếu ngày hoặc một dữ liệu khác. Vì vậy tách:

1. **Form nền:** các trường luôn hoặc thường cần theo loại automation.
2. **Form bổ sung:** sinh từ các biến BE chưa resolve được sau khi dựng context/template.
3. **AI `needs_input`:** chỉ dùng khi dữ liệu không đơn thuần bị thiếu mà còn mơ hồ hoặc có nhiều đáp án hợp lệ.

Ví dụ template release có `release_name`, `release_date`, `confirmation_owner`. BE tự điền trường đã biết và chỉ hỏi đúng trường chưa resolve. Nếu thiếu người thì dùng ô chọn người từ dữ liệu thật; nếu thiếu ngày thì dùng date picker. AI không tự bịa options.

### 54.4. Input là dữ liệu nghiệp vụ có kiểu, không chỉ là text ghép prompt

Một giá trị user nhập có thể được dùng đồng thời để:

- cung cấp context cho AI;
- chèn tên vào nội dung bài viết;
- mention đúng tài khoản trên hệ thống;
- gán assignee cho ticket Redmine;
- ghi audit.

Do đó người được chọn nên là `person_ref` có `displayName` và các ID nội bộ/connector liên quan, không chỉ là chuỗi tên. Schema có thể giới hạn `allowedUses`, ví dụ `ai_context`, `post_content`, `post_mention`, `ticket_assignee`, để AI không tự mở rộng mục đích sử dụng.

### 54.5. Phân chia trách nhiệm AI và BE

Thiết kế cần ba hợp đồng riêng:

| Hợp đồng | Trách nhiệm |
|---|---|
| Input schema | User cần cung cấp dữ liệu gì và FE render control nào |
| Decision schema | AI được phép đưa ra những quyết định nào, ví dụ có cần tạo ticket không |
| Action schema | Hệ thống được phép thực hiện action nào và mỗi action cần dữ liệu gì |

AI chỉ suy luận và trả action plan có cấu trúc, ví dụ `redmine.create_issue` và `drjoy.create_post`. BE phải validate action theo allowlist, resolve reference thành connector ID thật, kiểm tra quyền, dựng preview, yêu cầu approval trước external write, thực hiện connector và lưu kết quả/link. Không để AI tự do quyết định và gọi action ngoài schema.

### 54.6. Giới hạn UI để tránh biến thành workflow engine

UI không hiển thị JSON/schema kỹ thuật và không cần trở thành trình thiết kế workflow tổng quát. Chỉ cần các component tái sử dụng:

- text/textarea;
- ngày giờ;
- chọn một/nhiều giá trị;
- chọn người;
- chọn project/folder/kênh;
- xác nhận có/không;
- câu hỏi bổ sung;
- preview kế hoạch;
- kết quả từng action.

Preview phải diễn giải bằng ngôn ngữ người dùng, ví dụ: tạo ticket nào, gán cho ai, hạn ngày nào, đăng ở đâu và mention ai.

### 54.7. Phạm vi triển khai khuyến nghị

Không xây ngay dynamic workflow engine tổng quát. Nên làm một vertical slice:

- một automation cụ thể, ưu tiên “xác nhận release”;
- một số trường form cố định;
- tối đa một vòng AI hỏi bổ sung trong bản đầu;
- hai action rõ ràng: tạo ticket và đăng bài/mention;
- preview và approval trước khi thực hiện;
- sau UAT mới trích xuất pattern dùng chung.

BL-010 và BL-011 vẫn là nền UX nên cân nhắc làm trước: BL-010 làm rõ trạng thái đang chạy/chờ user/lỗi; BL-011 cho phép user sửa hoặc trả lời rồi kiểm tra lại ngay, không phải chờ scheduler. Phần CLI interactive của BL-004 nên thu hẹp thành fallback hoặc tách backlog riêng sau khi có bằng chứng form + `needs_input` không đủ.

### 54.8. Nhờ Claude phản biện trước khi chốt Change Spec

| Câu hỏi | Nội dung cần Claude đánh giá |
|---|---|
| Registry | Dùng chung registry automation hiện tại hay tạo `Automation Definition Registry` riêng? |
| Lưu input | Input động nên snapshot theo task definition hay từng occurrence? |
| Version | Version input schema thế nào để task cũ không bị hỏng hoặc đổi nghĩa? |
| Reference | `person_ref` nên resolve connector ID khi nhập hay ngay trước execute? |
| Safety | Ranh giới AI decision và deterministic BE validation đã đủ fail-closed chưa? |
| Approval | Nhiều action nên duyệt một lần theo plan hay duyệt từng action? |
| Scope | Vertical slice “xác nhận release” đã đủ nhỏ và có thể UAT chưa? |
| Backlog | Có nên đổi BL-004 sang form/context/action-plan và tách CLI interactive thành backlog ưu tiên thấp? |

**Điểm dừng:** đây là phương án đang thảo luận, chưa phải quyết định thiết kế cuối và chưa cho phép code. Nhờ Claude đọc code/kiến trúc hiện tại, phản biện các câu hỏi trên và đề xuất phạm vi Change Spec nhỏ nhất có thể triển khai an toàn.
